把一个 turn 从「一条线」变成「一张图」

这是一份关于「如何在 AO2 里用节点图编排 agent turn、把工程控制做到比主流 harness 高一阶」的设计方案。核心理念：确定的事交给硬编码的图拓扑，需要判断的事才切给小智力模型——人只在中断点出现，其余全自动。

Turn-as-Graph 智力分层调度 能力即组件 硬编码拓扑 + 小智力切点 全自动闭环 可观测 / 可干预 / 可恢复

§1用户视角:你坐在 TUI 前看到什么

不讲架构,先讲体验。这一节回答一个问题:这套东西做出来,用起来是什么感觉?

你打开 TUI,在输入框敲一句话——比如「给 observe 服务加一个按 harness_type 聚合的统计端点,带测试」。回车。 屏幕上不是开始刷一行行流式文本,而是长出一张图:一个发起节点,往下分叉成几个子任务(读现状/写实现/写测试),它们各自亮起、跑完汇合到一个收敛节点,最后落地成一个提交节点。 你看见哪个节点在转、哪个卡住了、哪个失败了。中间任何时刻你可以插手——暂停某个分支、改个方向、或者直接接管。跑完给你一屏:改了哪些文件、测试绿没绿、花了多少 token。

§2问题:主流 harness 的工程控制天花板在哪

要讲清楚「高阶在哪」,先得说清楚「现在的低阶在哪」。我们直接和 Claude Code / Codex / OpenClaw 摆在一起比。

工程控制维度 Claude Code / Codex OpenClaw AO2(本方案)
流程结构 无。一条对话流,工具调用线性串联 半。有多 agent,但编排靠 prompt 显式节点图。DAG/并行/收敛是数据结构
智力分配 All-or-nothing。一个超贵大模型从头干到尾 固定。每个 agent 绑死一个模型 分层调度。粗颗粒大模型主控,细颗粒小模型专项
记忆 黑箱。一个大 memory 块,不按任务维度 半。有记忆但耦合在 agent 内 组件化。记忆是可挂摘的 capability,按节点维度读写
工程知识承载 全靠 prompt。流程步骤藏在提示词里 全靠 prompt 硬编码拓扑。确定步骤是图结构,不是模型临场发挥
自动化程度 人全程盯。每步都要看 人全程盯 闭环。人只在共识+验收,中间全自动
可恢复 挂了重来。断了基本没了 挂了重来 事件溯源 + resume。断点续跑,不丢进度
可观测 流式文本。只能跟着看 流式文本 图 + 事件流。俯瞰全局,下钻细节

五个痛点,一句话各表

  • 线性:turn 是「一根线」,看不到全局结构,任务一复杂就迷路。→ 要变成一张图
  • 黑箱:模型脑子里怎么拆任务的、为啥走这步,你不知道。→ 拓扑要显式、要可见
  • 智力 All-or-nothing:简单子任务也用最贵的模型烧钱烧时间。→ 智力要按颗粒度分层
  • 记忆黑箱:一个大会话记忆,不区分是哪个任务沉淀的,越积越脏。→ 记忆要组件化、按任务维度
  • 不可恢复:长任务跑到一半断了,基本从头再来。→ 要事件溯源 + 断点续跑
关键洞察:这五个痛点本质是同一个病根——主流 harness 把「工程控制」整个外包给了一个大模型的临场发挥。流程、调度、记忆、恢复,全靠模型自己临场想。AO2 的思路是反过来的:能确定的部分,硬编码成图结构;只有真正需要判断的切点,才请模型出场。这是从「LLM-centric」到「engineering-controlled with LLM at the seams」的根本转向。

§3核心抽象:Turn-as-Graph

这一节把「一张图」这个直觉,落到 AO2 已有的代码地基上。结论是:三层已经齐了,只差把 turn 本身升格成图。

Turn-as-Graph 的意思是:一个 agent turn 不再是「调一次模型 + 一串工具」,而是一张可执行的节点图。这张图由三层支撑——执行引擎(workflow kernel,跑图)、注入系统(capability,给每个节点配指令和工具)、留痕层(observe,全程事件溯源 + 可恢复)。三层解耦,各管一摊。

三层地基(AO2 现状,代码级)

① 执行引擎 · workflow kernel

Pydantic spec 定义图,3 个原语:run(fan-out/fan-in 并行)、pipeline(无 barrier 阶段链)、loop(seen 去重收敛)。journal SQLite WAL 记事件,断点 resume。子 agent 零记忆(R1 红线)。

engine.py · journal.py

② 注入系统 · capability

9 层 capability 装配,每层自带指令段(get_instructions)和工具集(get_toolset),按序拼进 system prompt。Profile L0-L4 分层 + 动态层(多 cwd)。记忆/工具/守卫都是可挂摘的组件。

native_agent.py · capabilities/

③ 留痕层 · observe

独立进程 8002,SQLite WAL + WS subscribe。事件溯源:tick_started/tool_call/tool_result/tick_completed + flow/memory/orch 语义事件。挂了能从事件流重建状态。

observe/ · emit.py

§4六个高阶工程控制特点

这一节是「突破主流 harness」的核心。六个特点,每个都对应一个主流痛点,且都落在 AO2 已有的地基上。

① 节点图是一等公民

流程不再是藏在 prompt 里的隐式步骤,而是显式的数据结构(节点 + 边 + 依赖)。可序列化、可 diff、可版本化、可在 TUI 里画出来。主流 harness 的「流程」是模型临场想的,这里是你设计出来、存下来、可复用的工程资产。

治痛点:线性 + 黑箱

② 智力分层调度

不是全程一个模型。粗颗粒用大模型(glm-5.2 主控拆解),细颗粒用小模型(glm-4.7 专项执行)。调度决策本身也是可编程的:哪个节点该用多大智力,由图拓扑 + 节点 spec 决定,不是模型自己临场挑。

治痛点:All-or-nothing 智力 → 详见 §5.1

③ 能力即组件(capability)

记忆、工具、守卫、profile 都是可挂可摘的 capability。每个节点可以挂不同的能力组合——读现状的节点不要写权限,写实现的节点挂全工具,审查节点只读不写。能力随节点流动,不是全局一刀切。

治痛点:记忆黑箱 → 详见 §5.3

④ 确定流程 + 小智力切点

复杂工程的主体是确定性流程(先读、再写、再测、再审)——这部分硬编码成图拓扑,不烧智力。只在每个需要判断的切点(「这个实现对不对」「这个测试够不够」),请一个小而专的微调模型出场。工程知识在图里,不在 prompt 里。

治痛点:工程知识全靠 prompt → 详见 §5.4

⑤ 全自动闭环

从一句话到完成,人只出现两次:开头对齐共识(P1)、结尾验收(P4)。中间 P2 执行 + P3 回归全自动无人中断,异常才 push 通知。不是「自动助手」,是「自动工程师」。

治痛点:人全程盯 → 详见 §5.2

⑥ 可观测 / 可干预 / 可恢复

observe 全程事件溯源(SQLite WAL),journal 断点 resume。TUI 可视化每个节点状态。任意节点边界可设干预点——暂停、改向、接管。挂了不丢,接着跑。这是「工程系统」该有的可控性,不是「魔法黑盒」。

治痛点:不可恢复 + 不可观测

§5.1课题一:LLM 智力 与 task 颗粒度 的平衡

核心问题:什么时候用一个聪明大模型做整件事,什么时候拆成小颗粒用多个小模型?答案是——颗粒度由任务的确定性决定,不由大小决定。

调度第一原则:确定的部分用最弱的智力,不确定的部分才用强智力。一个任务越能被拆成确定的步骤,就越该用小颗粒 + 小模型;越是开放探索、需要临场判断,才越该用大模型整体处理。智力是稀缺资源,要花在刀刃(判断切点)上,不该均匀撒在每一步。

档位用在哪种任务模型 / effortAO2 原语

用大白话讲:你让一个人「写个完整功能」,他要懂全局、要会设计,得请高级工程师(大模型,贵)。但你让他「在这 10 个文件里找所有调用了 X 函数的地方」,这是体力活,实习生(小模型,便宜)并行干最快。聪明的活用聪明人,笨活用便宜人并行——但决定「哪个活该用谁」这件事本身,是项目经理(主控大模型)干一次就定的,不是每个活都重新想。

智力-颗粒度平衡的三个操作杠杆

node.model / effort
每个节点 spec 里直接写死该用哪个模型、多大 effort。这是硬编码的调度决策,不靠模型临场挑。WorkflowNodeSpec(model, effort)
fan_out 并发度
细颗粒任务用高并发(run + Semaphore),把 N 个独立子任务同时撒出去——便宜模型 × 并发 = 比一个贵模型串行更快更省。
schema_ref 结构化输出
判断切点用 schema 约束输出(schema_registry),把「自由发挥」收窄成「填表」——降低对智力的要求,小模型也能稳定产出结构化结论。
反模式警告:不要把所有节点都设成大模型高 effort——那是「用最贵的方式跑确定的流程」,既慢又烧钱,还不如主流 harness 一个模型串行。颗粒度分配本身就是工程设计的核心产出,这张智力分配图应该被 review、被存档、被复用。

§5.2课题二:全自动化设计

核心问题:怎么做到从一句话到完成,中间不打扰人,又能保证不出乱子?答案是——四阶段闭环,人只在两端,中间靠对抗验证 + 红线守恒。

自动化第二原则:自动化不是「放手让模型干」,是「把判断点提前到开头、把验证点铺满全程」。开头一次性把目标和边界对齐(共识),中间执行 + 验证全自动(对抗式 skeptic 兜底),结尾一次性验收。人不在中间出现,是因为中间该有的判断已经被设计进了验证节点——不是省略了,是结构化了。

P1共识

🎨 有人 · 把目标和边界一次锁死

需求理解(查代码/ADR/memory)→ 对齐范围、架构决策、验收标准 → 产出 spec + ADR + 编排图。这里 grill 到位,后面才不返工。提问预算:只有不可逆决策(MUST-ASK)才打断人,其余 agent 自决。

P2执行

🤖 全自动 · 按编排图拓扑推进

每个节点 spawn 独立 subagent(1 节点 = 1 subagent),拓扑序推进。每节点内部 implement → skeptic → fix(max 3 轮),对抗验证兜底。节点失败不阻塞依赖链,标记 out(failed) 继续。异常 push 通知,不暂停、不回问。

★ Turn-as-Graph 升格后:这里的「节点」就是图里的节点,P2 的推进 = 图的拓扑执行。
P3回归

🤖 全自动 · 全局视角收口

P2 每个节点独立 context 看不到彼此 → P3 做跨节点一致性审查(上游 commit 契约下游是否遵守、接口/类型一致、同名符号冲突)+ 回归测试 + ADR 对照。这是唯一的全局视角,补 P2 孤岛。

P4验收

🎨 有人 · 一屏报告 + 决策

一屏呈现:哪些节点 pass/fail、回归绿没绿、ADR 守没守、defer 了什么、改了多少文件。memory 沉淀踩坑。然后人决策:接受 / 回炉某节点 / 处理 defer。不写归档文档(git + memory 是事实归档)。

为什么中间能无人:不是「信任模型」,是「中间该拦的都拦了」。每个节点出口有 skeptic 审查(对抗式,默认反驳),每个依赖边界有契约检查,整体有 P3 全局审查。模型要是瞎搞,skeptic 会拦下、fix loop 会回头、P3 会抓出跨节点冲突。自动化靠的是验证结构,不是模型自觉。人省下来的精力,花在 P1 想清楚、P4 看明白——这两端才是人不可替代的。

三条自动化纪律(守不住就退化成「自动闯祸」)

  • 没有新鲜证据,不接受完成声明。节点说 pass 必须带 skeptic verdict + 测试结果,不信模型的自述。
  • 红线 grep 守恒(R1 子代理零 memory writer / R5 workflow 无 memory 事件 / RK11 注册名无 v2_ 前缀)——机械检查,任何节点不得违反。
  • 异常只 push 不暂停。失败标记后继续推进依赖链,不阻塞、不等人,把问题攒到 P4 一次性处理。

§5.3课题三:记忆组件化利用

核心问题:记忆怎么从「一个全局黑箱」变成「按任务维度、可挂可摘的组件」?答案是——记忆本身就是 capability,随节点流动,读写按节点 scope。

记忆第三原则:记忆不该是一个大池子,该是「这次任务沉淀了什么 / 这次任务该召回什么」的局部视图。每个节点有自己的记忆 scope:读现状的节点只读相关历史、写实现的节点沉淀这次的设计决策、审查节点读这次所有产出。记忆不是全局共享的污染源,是按节点/任务维度隔离的组件。

AO2 现状:记忆已经是 capability(地基齐了)

MemoryWriterCapability
inner wrap,wrap_run_event_stream 每轮 tool_result 自动沉淀(TURN_END + INGEST + KG + PRE_COMPRESS 四件套)。写记忆是自动的、按 turn 的,不需要模型主动调。
MemoryCapability
eager(高频),提供 experience_memory + kg_memory 工具,模型主动召回经验 + 知识图谱。读记忆是工具,按需的。
R1 红线
workflow 子 agent 零 memory writer——子节点不写记忆,避免 fan-out N 个节点各写各的污染主记忆。沉淀只在主控 turn 的 MemoryWriterCapability 发生。
现在记忆是怎么工作的:主控 turn 跑完一轮,MemoryWriterCapability 自动把这轮的工具结果、产出、token 消耗沉淀成经验 + 知识图谱(写是自动的)。下一轮模型需要历史时,用 MemoryCapability 提供的工具主动去召回(读是主动的)。子节点(workflow fan-out 出来的)不写记忆(R1)——它们是干活的,沉淀是主控的事。这已经比主流 harness 的「一个大 memory」强了:读写分离、自动沉淀、按 turn 维度。

组件化记忆的三个进阶设计(本方案要做的)

① 节点级记忆 scope

每个节点声明它的记忆 scope:读哪些 tag 的历史、沉淀到哪个 tag。读现状节点 scope=「架构现状」,审查节点 scope=「本次所有产出」。记忆隔离,不互相污染。

能力随节点流动(特点③)

② 图级记忆视图

一张图跑完,沉淀一份图级摘要(这次拆解成几个节点、每个节点结论、整体得失)——这是最有价值的「经验」,下次同类任务直接召回整个图的结构。

图即经验,可复用

③ 记忆作为可干预点

用户在 TUI 能看见「这次召回/沉淀了哪些记忆条目」,可以删错条、补对条、钉重要条。记忆不是黑箱沉淀,是可见可治理的资产。

§5.4课题四:硬编码级多专项 agent + 小智力微调模型分工

核心问题:怎么用一堆「笨但专」的模型,解决复杂工程化问题?答案是——复杂问题的大部分是确定的,硬编码成图;只有切点需要智力,用专项微调小模型填。

分工第四原则:工程化问题的主体是「确定的流程」,不是「需要天才的创造」。加个端点、写个测试、改个 bug——步骤是固定的(读现状→定位→改→测→审)。这部分硬编码成图拓扑(pipeline 的 stage 顺序 = 工程步骤),每个节点配一个专项 agent(特定 profile + 工具白名单 + 小智力模型)。工程知识活在图结构里,不活在 prompt 临场发挥里。只有「这个实现到底对不对」这种切点,才切给微调过的小模型判断。

三种「智力载体」的分工(关键区分)

载体承载什么形式智力需求
图拓扑流程步骤、依赖关系、并行/串行、收敛点硬编码(DAG/pipeline spec)零智力(确定)
专项 agent某类子任务的执行能力(读/写/测/审)profile + 工具白名单 + 小模型小智力(专项微调)
主控大模型需求拆解、跨节点仲裁、最终综合主控 turn + 图入口强智力(少用)
用大白话讲:盖一栋楼,「先打地基、再立柱、再封顶」这个顺序是建筑规范规定的(硬编码图拓扑),不需要每个工人都重新想。「怎么把这根柱子立直」是木工的专项手艺(专项 agent + 微调),不需要总工程师亲自干。只有「这栋楼整体结构合不合理」才要总工程师拍板(主控大模型,少用)。主流 harness 的问题是:让总工程师从挖地基干到封顶——又贵又慢又浪费。AO2 让总工程师只画图(图拓扑)和拍板,挖地基立柱子交给专项工(小模型)。

专项 agent 怎么造(落到 agents.yaml + capability)

AO2 已经有 agents.yaml 持久化(现在两个 agent:native 专员 + main 助理)。专项 agent 就是给 agents.yaml 多写几条,每条配死它的「手艺」。

# 专项 agent 矩阵示例(本方案要扩的): - id: reader # 读现状专员 · 细颗粒 model: glm-4.7 tools: {allow: [v2_file_read, v2_search, kg_memory]} # 只读不写 profile: [L0:你是代码侦察兵,只摸清现状不改动] - id: implementer # 实现专员 · 中颗粒 model: glm-4.7 tools: {allow: [v2_file_read, v2_file_write, v2_search]} profile: [L0:你是一个专注的实现者,只改必要的地方] - id: tester # 测试专员 · 中颗粒 model: glm-4.7 tools: {allow: [v2_file_read, v2_file_write, v2_bash]} profile: [L0:你只写测试,覆盖被改逻辑的边界] - id: skeptic # 审查专员 · 中颗粒(对抗) model: glm-4.7 tools: {allow: [v2_file_read, v2_search]} # 只读,绝不写 profile: [L0:你的默认立场是反驳,找出实现的漏洞] # 主控(已存在): - id: main # 全能助理 · 粗颗粒,需求拆解+综合 model: glm-5.2 effort: high
「微调」在这里的含义:不是指模型权重微调(成本太高、不通用),而是通过 profile 指令 + 工具白名单 + schema 约束,把一个通用小模型「框」成专项。glm-4.7 本身是通用的,但配死「只读 + 你是侦察兵 + 输出固定 schema」,它在这个窄任务上就表现得像「专门调过」的。这是穷人版微调,但够用、可复用、可组合。真有钱有数据了,某个高频节点(比如 skeptic)再上权重微调,是平滑升级路径。

§7落地路径:基于现状,分三阶段

三层地基已齐(workflow kernel + capability + observe),只差「turn 升格成图」。分三阶段,每阶段都可独立验证、不破坏现有红线。

P0通气

给 workflow kernel 补 DAG + 条件边

现状只有 run/pipeline/loop。加一个 graph 原语:节点 + 边 + depends_on + 条件边(上一节点结果决定下游走哪条)。复用 journal 的 SQLite WAL resume(已有)。这一步把「图」从「隐式」变「显式」,是 Turn-as-Graph 的地基。

缺口:engine.py 现无 DAG/条件分支/depends_on。这是 §3 指出的核心缺口。
P1升格

让 turn 入口能承载图(不只是单次 run)

现在 turn = 一次 Agent.run。在 trigger_turn 里加图分派:主控模型输出图 spec(或从模板取)→ 图执行引擎跑 → 事件全程 emit observe。专项 agent 矩阵(reader/implementer/tester/skeptic)扩进 agents.yaml。这一步 turn 真正变成图。

P2可视
