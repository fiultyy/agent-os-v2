对话与编排核心

module · orchestrator
这是整个 Agent OS 平台的"大脑中枢":用户在网页里向 Agent 提问或下达任务,这个模块负责把请求接进来、决定由哪个 Agent 处理、把上下文(对话历史+长期记忆+可用工具)组装好交给大模型、按需调用工具完成任务,再把回答以流式(SSE)实时推回前端。它还支持多 Agent 编排——把一个大任务拆给若干角色子 Agent 并行思考,再由一个主 Agent 综合出统一答案。一句话:它让用户能像和真人助理团队对话一样使用 Agent OS,且过程对用户实时可见。
🧩 业务处理流
用户在前端(ExecutePanel/OrchestrationPanel)输入问题并选择 Agent,前端 POST 到 /v1/execute(单 Agent)或 /v1/orchestrate(多角色编排)。后端先用 ConcurrencyController 拿执行槽位,构建对应 StateGraph(单 Agent 线性工具循环图 / 多角色并行图),用 GraphState 装入用户输入;图逐节点执行——start 初始化、llm 节点由 ContextCompiler 召回记忆并组装三层上下文后调 LLMClient(双通道)请求大模型,若模型发起原生 tool_use 则进 tool 节点由 ToolExecutor 执行并把结果回注循环(最多 MAX_TOOL_ITERATIONS 轮防死循环),最后 llm_synthesize 综合工具历史产出最终答案;每节点完成经 on_node_complete 把状态推入 asyncio.Queue,SSE event_stream 以 event:node_start/node_complete/agent_status/execution_complete 流式吐给前端;同时对话与工具结果经 memory_event_bus 异步沉淀为长期记忆、KG 抽取实体、pitfail 记录工具失败,会话结束时触发会话→情景记忆迁移。多 Agent 编排则把任务 fan-out 给若干临时子 Agent 并行思考、fan-in 汇聚视角、由主 Agent 综合并单点落库。
1
接收请求并装配执行槽 — 前端 POST /v1/execute 或 /v1/orchestrate,后端校验 Agent 存在、生成 session_id、把 Agent 注册进 CommunicationBus 会话、触发 SESSION_START 记忆事件
ConcurrencyController.acquire_agent_slot 拿信号量限并发;register_agent 使广播收件人非空;agent.status 置 running
2
构建编排图 — 按请求类型 _build_execution_graph()(单 Agent: start→llm→tool→llm_synthesize)或 _build_multi_agent_graph(P3: multi_agent ParallelNode→fan_in→synthesizer)
条件边 _llm_route 按 needs_tool 和 tool_iteration<MAX_TOOL_ITERATIONS 决定继续工具循环或综合;图挂 InMemoryCheckpointStore
3
组装上下文并调用大模型 — _node_llm 把 system_prompt+会话历史+工具历史交给 ContextCompiler.compile,产出三层 messages 后调 LLMClient.chat(tools=原生工具 schema)
R2 contract:召回记忆注入当前 user 消息尾 <memory-context> 而非独立 system;static_count 标记静态前缀供 anthropic cache_control;模型发起 tool_use 时 last_tool_use 解析为 {name,input}
4
执行工具并回注循环 — 若有 tool_use,_node_tool 经 ToolExecutor 查注册表→Guardrail 校验→超时执行 handler→校验输出,记录 {tool_use,tool_result} 进 tool_use_history 并递增 tool_iteration,然后图边 tool→llm 回到上一步
失败时 PitfailRegistry 按 match/increment 或 record 记复发;MAX_TOOL_ITERATIONS(默认5)防死循环强制综合;工具结果异步存为 working 记忆
5
综合最终答案 — _node_llm_synthesize 把完整工具历史(每轮 tool_use→result 串成可读 transcript)拼进 user 尾,调 LLMClient 产出综合回答
R2:工具结果注入 user 尾不作独立 system;综合回答触发 KG 实体抽取(fire-and-forget)
6
SSE 流式推送进度 — on_node_complete 回调把每个节点 start/complete 状态推入 asyncio.Queue,event_stream 协程以 SSE 文本吐给前端,末尾发 [DONE]
事件类型:agent_status/node_start/node_complete/execution_complete/error;前端 sse-dispatch 分发到对应面板;并发槽在 finally 释放
7
异步沉淀记忆 — 经 memory_event_bus 触发 TURN_END(working 记忆核心存储)→SESSION_END(会话→情景迁移 fire-and-forget)→INGEST(IngestorAgent KG 抽取,feature-gated),任务结束触发 TaskConsolidator 在线复盘
WriteQueue 有界并发池+per-agent 排序;后台 MemoryDBWatcher 轮询外部 DB 写触发零LLM确定性维护链(prune/forget/migrate);降级开关 MEMORY_EVENT_BUS_ENABLED=0

用户与 Agent 对话时,记忆系统的运作对用户是隐形的:每个 turn 结束,chat.py 通过事件总线触发 TURN_END,DefaultMemoryHook 把 LLM 工作记忆(working)和工具结果(working)迁移到 session 层并打分;当对话上下文逼近 token 上限(70%/85%),ContextMonitor 触发压缩——异步或同步地把低价值记忆分组摘要成新的 semantic 项、归档原文,把腾出的空间通过 SSE 推给前端。会话结束时,session 记忆迁移到 episodic(跨会话经验层)。在后台,MemoryDBWatcher 持续轮询 SQLite 的 updated_at 水位,一旦检测到外部进程写入且进入写空闲窗口,就分三档触发:先跑零成本确定式链(状态裁剪→遗忘→迁移),再唤醒 ①IngestorAgent 用 LLM 把自沉淀(origin=AGENT)记忆抽成实体关系注入知识图谱并打身份标签,最后 ②ConsolidatorAgent 把零散 episodic 经验语义合并成 coherent 的 semantic 认知;④CuratorAgent 在更闲时做离线 QA(归档冗余/合并/纠错)。用户主动查询时,recall 走 Keyword+KG 双路融合召回,③RetrieverAgent 用神经场 lif 权重做 match×lif 重排;Agent 自己也能通过 KGMemoryTool/ExperienceTool function-call 直接查图谱、查高复用经验、打包技能 bundle。整个过程中 FOREGROUND(用户手输/外部应用直写)记忆被红线保护,永不自动消化/归档/合并,确保用户数据主权不丢。

工具系统

module · tools
工具系统是 Agent 的"手脚":它把大模型决策出来的动作(发 HTTP、读写文件、查数据库、读改搜代码、跑代码审查、自动化浏览器操作)变成可被安全调用、可被统一管理的标准工具。它存在是为了让 Agent 不只是"会说",而是"会做"——同时通过护栏挡住危险指令(如 rm -rf、路径穿越)和敏感信息泄漏(如 password/token),让 Agent 行为可控可审计。
🧩 业务处理流
用户和 Agent 对话时,大模型在每轮回复里如果决定要做事,会以 Anthropic 原生 tool_use 块的形式给出工具名和参数。编排图把这个 tool_use 路由到工具执行器:执行器先从注册表里找到对应 handler,然后让护栏检查输入参数(挡掉危险命令和路径穿越),通过后用 asyncio.wait_for 限时跑这个 handler(无论是 HTTP 请求、文件读写、数据库查询还是代码搜索),跑完再让护栏扫一遍输出(挡掉密码、密钥、token 泄漏),最后把 status(success/blocked/timeout/error)和 output 拼成 tool_result 回注给下一轮 LLM,模型基于真实工具结果继续对话或结束。整个多轮工具循环有硬上限防止死循环。代码审查和浏览器流程是更高层的复合工具,内部编排多个原子步骤(navigate→click→type、code_read→search→分析报告),但因重依赖当前未在主链注册。

多 Agent 协同

module · multi-agent
让一个"主 Agent(orchestrator)"像团队 leader 一样,把一个复杂任务拆给 N 个不同角色的"子 Agent"(researcher/coder/reviewer 等)并行处理,再把它们的输出综合成一个统一答案。它解决了单 Agent 单线思考视角单一、串行慢的问题:用户一次提问就能拿到多视角并行调研 + 自动综合的结果。同时它还提供 Agent 之间互相发消息(单聊/群广播/话题订阅/请求-响应)、并发限流(防止同时跑爆 LLM 配额)、以及可见可观测的实时进度推送。

PitFail 踩坑库 ⚠️

module · pitfail
当 Agent 在执行工具调用(http_get / file_read / web_search 等)失败时,系统自动把这次"踩坑"(哪个工具、什么错误类型、什么症状、根因、怎么修)记进一个持久化的踩坑库,并在下次同类失败发生时累加复发计数。这样平台就拥有了一份"工具失败知识库",可按症状关键词模糊搜、按 (工具名, 错误类型) 精确定位,辅助排查与回归——让 Agent 系统能"记住曾经踩过的坑",而不是每次都从零失败。
🧩 业务处理流
用户视角的处理链路是:Agent 在编排运行中调用某个工具(如 http_get、file_read),ToolExecutor 执行后若 status != success,平台在 chat.py 的 _node_tool 节点里先用 _classify_tool_error 把错误消息归类为 timeout/file_not_found/permission_denied/tool_error 四类之一,然后拿 (工具名, 错误类型) 去 registry 精确 match;若已有踩坑记录就只把 recurrence_count 加 1(说明这个坑又踩了一次),若没有就用错误消息作 symptom/root_cause 新建一条记录(recurrence_count=1)。整个过程被 try/except 静默包裹,任何 pitfail 异常都不会阻断主工具流程(零回归)。与此同时,用户或前端可以通过 GET /v1/pitfall/ 看全部踩坑列表、用关键词搜 symptom/root_cause/fix、用 (file_path, error_type) 精确匹配、或按 id 取单条——这些是纯查询端点,用于排查与回归时翻看"系统都踩过哪些坑、哪些最常复发"。

Agent Profile / Agent 定义与生命周期

module · agent-profile
这是 Agent OS 平台的"智能体身份中心":负责创建、存储、定义每一个 Agent(助手)——它叫什么、用什么大模型、系统提示词是什么、配什么工具,以及在多 Agent 编排中临时"召唤/销毁"子 Agent。它解决了"用户如何在这个平台里拥有一个或多个可对话、可分工的 AI 助手"的核心问题:用户开箱即得一个默认中文助手,也能自己创建/删除/查看任意数量的 Agent,并让多个 Agent 协同完成一个复杂任务(并行分析、多角色 fan-out 后综合)。
🧩 业务处理流
用户视角:首次打开平台,系统自动准备好一个"默认助手"(中文、glm-4-flash),用户可直接对话;用户也能在 Agent 管理界面自己创建新 Agent(填名字、选模型、写系统提示词、勾工具)或删除/查看已有 Agent,这些操作实时持久化到 PostgreSQL,服务重启后自动恢复。当用户要解决一个复杂任务时,可在多 Agent 编排界面指定一个"主 Agent(orchestrator)"和多个"子 Agent 角色(researcher 等)",系统会为每个角色临时召唤一个子 Agent 各自跑一轮 LLM 对话,然后把多份回答汇总交给主 Agent 综合成最终答案,子 Agent 用完即销毁不沉淀长期记忆——这就是 fan-out → fan-in → synthesize 的多智能体协同闭环。

API 网关

module · api-gateway
这是整个 Agent OS 平台对外的统一入口和"门卫"。前端浏览器、外部脚本以及内部服务都不直连后端各微服务,而是统一打到网关,由它完成三件事:一是把 HTTP 请求按路径转发给真正干活的 orchestrator(或归档中的辅助服务 prompt-manager / resource-manager),二是用 JWT(RS256 非对称签名)做登录/换 token/刷新/吊销和接口鉴权,三是给认证接口做按 IP 的限流、给跨域请求加 CORS。没有它,前端就得知道每个微服务的地址和各自的鉴权方式;有了它,前端只需认准一个地址、带上一个 token 即可调用全部能力。
🧩 业务处理流
用户(或前端)先用预共享 API key 调 POST /auth/token 换取一对 JWT(access 15 分钟 + refresh 7 天),随后每次调用业务接口都在 Authorization 头带上 access token;网关经 require_auth 校验 RS256 签名与 access 类型后,按路径前缀把 JSON 请求原样 HTTP 转发给 orchestrator(/v1 前缀)或辅助服务,orchestrator 返回的 JSON 直接透传回前端。当用户发起执行/编排(/execute、/orchestrate、/agents/{id}/run)时,网关改用 httpx.stream 拿到上游的 SSE 文本流,以 StreamingResponse 边收边发地推回前端(中间还把前端习惯用的 message 字段归一化成 orchestrator 要的 input)。access token 过期后,前端用未过期的 refresh token 调 /auth/refresh,网关校验、把旧 jti 写入 SQLite 黑名单、再签发新的一对 token。归档中的 prompts/resources 两类接口因上游未通电,经 _aux_call 统一返回 502 而非 5xx 噪声。
1
换发 JWT — 客户端用 API key 调 POST /auth/token,网关校验 key 在 AUTH_API_KEYS 内,以 sha256(key) 为 sub 签发 access(15min)+refresh(7d) RS256 token
限流依赖 rate_limit_auth 按 IP 滑窗 10次/60s;密钥来自 data/keys/jwt_*.pem(缺失时启动自动生成 2048 RSA)
2
鉴权拦截 — 业务路由经 Depends(require_auth):AUTH_ENABLED=false 直通;true 则校验 Bearer JWT 的 access 类型,失败 401,并把 claims 写入 request.state.user/token_claims
/health 与 /auth/* 及 /docs /openapi.json /redoc 列入 PUBLIC_PATHS 白名单免鉴权
3
JSON 请求转发 — 非流式路由(agents/memories/messages/kg/debug/chat)把 request.json() 透传到 {ORCHESTRATOR_URL}/v1/<同路径>,raise_for_status 后原样回传 JSON
共享 httpx.AsyncClient(timeout 60s);测试用 MockTransport 断言路径必带 /v1
4
SSE 流式透传 — 流式路由(/execute /orchestrate /agents/{id}/run)用 httpx.stream POST 上游,aiter_lines/aiter_text 逐块 yield,StreamingResponse media_type=text/event-stream 回推
execute 做 message→input 字段归一化(BFF);execute 超时 120s、orchestrate 300s;headers 含 Cache-Control:no-cache / X-Accel-Buffering:no 防代理缓冲
5
token 刷新与吊销 — POST /auth/refresh 校验 refresh token,把旧 jti INSERT 进 SQLite revoked_jtis 表(轮换不可重用),签发新对;POST /auth/verify 仅判合法返回 claims
SQLite WAL+NORMAL,异常降级为内存 set;两端点均过 rate_limit_auth
6
归档上游兜底 — prompts(→prompt-manager:8002)、resources(→resource-manager:8004)经 _aux_call,任何 HTTPStatusError/ConnectError/RequestError 统一返回 502 'upstream aux service not wired'

7
服务级健康检查 — GET /health 经 Depends(require_service_key) 校验 X-Service-Key 头(未配 SERVICE_AUTH_KEY 时直通),返回 {status: ok}
供内部服务/容器编排做存活探针,与用户 JWT 鉴权通道分离

前端画布与 Agent 交互层

module · frontend-canvas
这是 agent-os-v2 平台的用户操作入口,把后端的 Agent 执行、多 Agent 编排、记忆、调试等能力包装成可视化界面。用户在这里能用自然语言和单个 Agent 对话(首页对话窗)、拖拽拼装 Agent/Tool/Prompt 节点编排工作流(画布页)、实时观察一个会话里 Agent 的每一步思考与工具调用(实时画布页 WebSocket 事件流)、管理 Agent 列表、检索四层记忆、回放执行历史,以及做单/多 Agent 的调试。它解决的核心问题是:让用户看得见 Agent 在干什么、插得进手去控制它,而不是面对一个黑盒 API。
🧩 业务处理流

辅助服务(提示词管理 + 资源管理 + gRPC 协议预留)

module · aux-services
这模块是给 Agent 平台提供两类"配套基础设施"的辅助服务:一是把散落在各处的 Prompt 文本统一存成可版本管理、可变量渲染的模板(避免硬编码提示词、支持回滚);二是把多家大模型厂商(OpenAI/Anthropic/智谱)统一抽象成可注册、可按别名路由、可选最便宜的"资源池"。当前两个服务都已被归档(profiles:[aux],默认不启动),前端的 gateway 代理也仅保留兜底返回 502,真正在用的只是 providers 适配器代码被其它模块的 LLM 调用所参考。同时 packages/proto 下放了一套 gRPC 的 .proto 定义,作为未来换协议的接口契约预留,但目前未生成代码、未接线。
🧩 业务处理流
从用户视角看,Prompt 侧:用户在前端/CLI 写一段带 {{变量}} 占位符的提示词文本,通过 gateway POST /prompts 创建模板,系统自动扫描出变量、存为内存记录并建立第 1 号版本;之后改内容会自动产生新版本号,可随时列版本/回滚到旧版本;真正要给 Agent 用时,POST /prompts/{id}/render 传入变量值,模板引擎把占位符替换成实际内容返回最终 prompt 文本。Resource 侧:用户先把 LLM 厂商(provider)登记进来,再把"逻辑别名(如 fast-cheap)"绑定到具体 provider+真实 model_id 上并标注单价;运行期任意服务拿一个别名 POST /route/resolve 即可拿到该走哪个 provider 的哪个模型,也可 POST /route/cheapest 让系统按输入单价挑出最便宜的可用模型;真正调用时 provider 适配器(OpenAI/Anthropic/智谱)会带 API Key 向对应厂商发 HTTP 请求,遇到 429/5xx 自动指数退避重试,流式请求解析 SSE data: 行。当前两服务默认不启动,gateway 调用时直接拿到 502「upstream aux service not wired (archived)」。

2

register_model 校验 provider 是否存在(注册表/内置/按 name 查询),写入 _models[alias] 并同步 _router.add_route;PromptVersion 版本号 = len(versions)+1,版本含 content+metadata
3

PromptTemplate.render 把 {{var}} 正则替换成 {var} 后调 str.format;KeyError(缺变量)被捕获返回 error;ModelRouter.resolve 是 dict.get 单跳查表
4
选最低价模型(可选) — POST /resources/route/cheapest 按 provider 过滤 + 仅 enabled,选 cost_per_1k_input 最小的
min(candidates, key=lambda m: m.get('cost_per_1k_input', inf));无候选返回 502/No available models
5
调真实 LLM(provider 适配器) — providers 适配器用 httpx.AsyncClient 向 OpenAI/Anthropic/智谱发 chat/completions 或 messages 请求
Anthropic 把 messages 里 role=system 抽出合并到顶层 system 字段(非 messages);带 x-api-key+anthropic-version header;429/500/502/503/504 走指数退避(MAX_RETRIES=3, BACKOFF=1*2^attempt)
6
流式返回(SSE) — provider.stream() 以 async generator 逐块 yield 文本
OpenAI/智谱解析 'data: ' 前缀行,[DONE] 终止;Anthropic 解析 content_block_delta 事件的 delta.text;连接建立失败才重试,已开始流不重试
7
回滚模板(可选) — POST /prompts/{id}/rollback/{version} 把模板内容恢复到指定版本
查到目标版本后覆盖 t['content']、重扫 variables、调 vs.create_version(content, {'rollback_from': version}) 形成新版本(不留破坏性删除)
